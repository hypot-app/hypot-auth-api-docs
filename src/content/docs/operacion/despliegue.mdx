## Las reglas que más fallan

| Ajuste | Regla |
|--------|-------|
| `AUTH_PUBLIC_BASE_URL` | En producción, una URL `https` sin barra final, sin query y sin fragmento, por ejemplo `https://auth.example.com`. Se copia tal cual en el `iss` de cada token y de ella sale la URL de la JWKS. **El servicio se niega a arrancar** con cualquier otro valor. |
| `TRUST_PROXY` | Pon el número de saltos o los CIDR de los proxies delante de Auth (por defecto `false`). Sin configurarlo detrás de un balanceador, todos los clientes comparten la dirección del proxy: un usuario puede agotar el límite de IP de todos. Si lo pones de más, un `X-Forwarded-For` del cliente prevalece. La ventana de gracia del refresh también depende de este valor. `true` se rechaza. |
| Contadores | `abuse_counters` es una tabla `UNLOGGED`: rápida, pero sin recuperación tras un fallo ni replicación. Tras un fallo o un cambio de servidor queda vacía y cada ventana y bloqueo empieza de nuevo, lo cual solo perdona. |
| Migraciones | Se aplican antes de la versión nueva, con un trabajo aparte. Cada ejecución de `migration:revert` deshace una migración. |
| Base de datos | Cada proceso mantiene como máximo 10 conexiones (constante `DB_POOL_MAX`, no una variable de entorno). **Réplicas por 10 debe caber en `max_connections` de Postgres**, menos una reserva para migraciones y operadores. |

<Aside type="caution" title="Si en producción las URL de tus apps son http">
Con `NODE_ENV=production`, la CLI rechaza orígenes y URL `http` (solo se aceptan para `localhost` y `127.0.0.1` fuera de producción). Registra tus apps con `https`.
</Aside>

## Tras un balanceador

Detrás de un balanceador con TLS:

1. El balanceador termina HTTPS y habla HTTP con Auth. Auth lee la IP del cliente de `X-Forwarded-For` según `TRUST_PROXY`.
2. `AUTH_PUBLIC_BASE_URL` es la URL pública `https` que ven tus consumidores (la misma que el emisor `iss`), no la dirección interna.
3. Comprueba con una petición real que los bloqueos y límites distinguen a los clientes: si todos los intentos de login de distintas personas se bloquean entre sí, `TRUST_PROXY` está mal.

## Cierre ordenado y salud

- Cada réplica ejecuta sus propios trabajos de segundo plano (envío de correos, limpieza de contadores y retención). Es seguro tener varios: la cola de correos usa `FOR UPDATE SKIP LOCKED` y los barredores solo borran.
- Al recibir `SIGTERM`, cada trabajo deja de programarse y termina el lote en curso antes de cerrar el pool. Da al contenedor un periodo de gracia de **70 segundos** (el envío de un correo tiene un plazo de 60 s).
- La imagen incluye un `HEALTHCHECK` que consulta `/health` (que a su vez hace un ping a la base de datos).

## El compose de la API es solo para desarrollo

El `compose.yaml` del repositorio de la API usa una URL `http`, `NODE_ENV=development`, secretos de desarrollo y claves de desarrollo generadas. **No lo uses para desplegar.** Su servicio `migrate` ejecuta el mismo comando de este documento y la API espera a que termine con éxito.
